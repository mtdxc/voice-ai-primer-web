1. 2026 年的对话式语音 AI

LLM 是出色的对话者。

如果你曾花大量时间与 ChatGPT 或 Claude 进行自由对话，你会直观地感受到：与 LLM 交谈相当自然，而且用途广泛。

LLM 还擅长将非结构化信息转化为结构化数据。[1]

语音 AI 智能体利用 LLM 的这两项能力——通过对话，从非结构化数据提取结构——并创造一种全新的用户体验。

[1] 这里是广义的，而非指某些 LLM 的“结构化输出”功能这一狭义概念。

如今，语音 AI 正部署在许多业务场景中，比如：

  • 在医疗预约前收集患者数据，
  • 跟进呼入的销售线索，
  • 处理种类日益繁多的呼叫中心任务，
  • 求职面试与用户研究访谈，
  • 在企业之间协调日程与物流，以及
  • 为几乎所有类型的小型企业接听电话。

在消费者端，对话式语音（和视频）AI 也开始进入社交应用和游戏领域。开发者们每天都在 GitHub 和社交媒体上分享个人语音 AI 项目与经验。

4. 基本的对话式 AI 循环

语音 AI 智能体最基本的“待完成任务”是：聆听人类说的话，以某种有用的方式回应，然后重复这一过程。

如今生产环境中的语音智能体几乎都有非常相似的架构。语音智能体程序在云端运行，并编排语音到语音的循环。该智能体程序使用多个 AI 模型：有些在智能体本地运行，有些通过 API 访问。智能体程序使用 LLM 函数调用或结构化输出，来与后端系统集成。

  1. 语音由用户设备上的麦克风采集，经过编码后，通过网络，发送到在云端运行的语音智能体程序。
  2. 输入语音被转录，为 LLM 提供文本输入。
  3. 文本被组装成上下文——即提示词——然后由 LLM 执行推理。推理输出通常会由智能体程序进行逻辑过滤或转换。[5]
  4. 输出文本被发送到文本转语音模型，生成音频输出。
  5. 音频输出被发送回用户。

你会注意到，语音智能体程序运行在云端，文本转语音、LLM 和语音转文本处理也都在云端进行。从长远来看，我们预计会有更多 AI 工作负载在设备端运行。但今天，生产环境的语音 AI 尤其以云端为中心，原因有两个：

  1. 语音 AI 智能体需要使用当前最好的 AI 模型，才能以低延迟可靠地执行复杂的工作流。终端用户设备目前还不具备足够的 AI 算力，无法以可接受的延迟，来运行最好的 STT、LLM 和 TTS 模型。
  2. 如今大多数商业语音 AI 智能体都是通过电话与用户通信的。对于电话通话而言，并不存在终端用户设备——至少没有一个可运行代码的设备！

5. 核心技术与最佳实践

5.1. 延迟

构建语音智能体在大多数方面与其他类型的 AI 工程类似。如果你有构建基于文本的多轮 AI 智能体的经验，那么这些经验中的大部分在语音领域同样有用。

最大的区别在于延迟。

在正常对话中，人类期望快速的回应。500 毫秒是典型的的响应时间。长时间的停顿会让人觉得不自然。

如果你在构建语音 AI 智能体，学习如何从终端用户的角度准确测量延迟是很有价值的。

你经常会看到AI平台呈现的延迟并非真正的“语音到语音”测量。 这通常不是出于恶意。从服务商的角度来看，测量延迟的简单方法就是测量推理时间，因此服务商习惯了以这种方式思考延迟。然而，这种服务器端视角没有考虑音频处理、语句端点检测延迟、网络传输以及操作系统开销。

手动测量语音到语音延迟很容易。

只需录制对话，将录音载入音频编辑器，查看音频波形，然后测量从用户说话结束到 LLM 开始说话之间的时间。

在为生产环境构建对话语音应用时，偶尔通过这种方式查看延迟数据是值得的。 如果能在测试中模拟网络丢包或抖动，那就更好了！

以编程方式测量真正的语音到语音延迟具有挑战性。部分延迟发生在操作系统深处，因此大多数可观测性工具只测量首个（音频）字节的到达时间。这是总语音到语音延迟的一个合理近似指标，但同样请注意，你没有测量的东西——比如语句端点检测的波动和网络往返时间——如无法跟踪，就可能成为问题。

如果你在构建对话式 AI 应用，1500 毫秒的语音到语音延迟是一个值得追求的重要目标。以下是从用户麦克风到云端再返回的、一次语音到语音往返的时间分解。这些数字相当典型，总计约为 1200 毫秒。因此 1500 毫秒是有挑战性的——如果你的电话服务商增加了几百毫秒，就会超出预算——但借助当今最好的 AI 模型和 Pipecat 这样高效的框架，这是可以实现的。

5.2. 面向语音场景的 LLM

2023 年 3 月 GPT-4 的发布开启了当前的语音 AI 时代。GPT-4 是第一个既能维持灵活的多轮对话、又能被足够精确地提示以完成有用工作的 LLM。

如今，语音智能体使用最广泛的模型是 GPT-4.1、GPT-5.1 和 Gemini 2.5 Flash。

这些模型兼具：

  • 低延迟。
  • 良好的指令遵循能力。[8]
  • 可靠的函数调用。[9]
  • 较低的幻觉及其他不当响应的发生率。
  • 稳定的性格与语气。
  • 相对较低的成本。

最近，有几个模型系列正在智能与延迟的帕累托前沿上挑战 GPT 和 Gemini 模型系列。

你会注意到 GPT-4.1 和 Gemini 2.5 Flash 都是相对较老的模型。这两个家族的新模型都是“推理”模型，生成内容 token 的速度会慢得多。Gemini 3 尤其慢，因此尽管它们在智能基准测试上表现优异，通常我们还是无法将其用于语音智能体。

不过，我们的方法自语音代理构建早期以来已经不断演变。2024 年，我们花了大量时间说服人们智能体可以“像人类一样快速”地回应。如今，我们从为各种用例部署真实语音智能体的过程中获得了大量实证证据：人们乐于与 1500 毫秒内作出回应的智能体交谈。

但至关重要的是，不要出现延迟尖峰，也不要在为智能体添加工具调用等功能时让延迟逐渐攀升到 1500 毫秒以上。由于延迟对语音场景如此重要，本指南将频繁讨论延迟问题。

5.2.3 那语音到语音模型呢？

语音到语音模型 可以用音频（而非文本）进行提示，并能直接生成音频输出。这就省去了语音智能体编排循环中的语音转文本和文本转语音环节。

语音到语音模型的潜在优势包括：

  • 更低的延迟。
  • 更好地理解人类对话中细微之处。
  • 更自然的语音输出。

OpenAI、Google 和 AWS 都通过各自的 API 提供语音到语音模型。NVIDIA 和其他几家研究实验室也已发布语音到语音的演示和研究成果。

语音到语音模型在遵循指令和调用工具方面不如文本模式的 LLM 可靠。它们还更慢、更贵、可配置性更差，也更难集成到真实的智能体系统中。

另一方面，当今最好的语音到语音模型听起来确实非常自然。OpenAI的GPT-realtime模型听起来仿佛真正预见了语音AI的未来

以下是语音到语音模型与文本模式 LLM 目前的对比情况：

  • 从理论上讲，语音到语音模型可以实现更低延迟，但音频比文本消耗更多 token。更大的 token 上下文会让 LLM 处理得更慢。实际上，如今OpenAI和谷歌的语音转语音模型都比调校良好的级联（多模型）语音代理慢
  • 更好的理解能力似乎是这些模型的一项真实优势。这在 Gemini 2.5 Flash 和 Gemini 3 Flash 的音频输入上尤为明显。
  • 如今，更自然的语音输出是可以明显感知到的。在测试中，大多数用户认为最好的语音到语音模型的输出比独立的文本转语音模型的输出更自然。
  • 语音到语音模型的 API 在灵活性上远不能满足生产环境语音智能体工程的需要。企业级语音智能体需要进行大量的上下文操作和摘要。这在 OpenAI Real-time API 上是可以做到的，但由于该 API 维护着自己内部的对话上下文版本，状态管理颇为棘手。而 Gemini Live API 则完全无法进行复杂的上下文操作，最好将其视为尚未准备好投入生产环境的 alpha 版本。
  • 语音到语音 API 无法提供快速或可靠的转录。如果你需要准确转录用户输入，以满足合规要求、下游评测（Evals）或在应用 UI 中使用，那么语音到语音 API 提供的转录可能不够好。
  • 对于输入为混合语言语音的用例，语音到语音模型的表现远远优于多模型流水线。例如，语言学习应用就从语音到语音模型的这一优势中受益匪浅。

同样值得注意的是，语音到语音 API 仍然相对昂贵。我们构建了一个 OpenAI Real-time API 成本计算器，展示成本如何随会话时长增长，并把 OpenAI 非常好用的自动 token 缓存功能考虑在内。用 OpenAI Real-time API 构建的智能体比用 GPT-4.1 构建的智能体贵 3 到 5 倍。

我们预计语音到语音领域会持续进步。但生产环境的语音 AI 应用从多模型方案转向使用语音到语音 API 的速度有多快，仍是一个未知数。

5.3. LLM 基准测试

5.3.1 智能/延迟帕累托前沿

在为智能体选择 LLM 时，智能水平、延迟和成本都是重要因素。

由于延迟对语音智能体尤为重要，我们常常被迫做出权衡：使用一个没有我们期望的那么“聪明”、但 TTFT 更快的模型。

这一点尤其成立，因为在过去两年里，基础模型实验室一直专注于推理模型，这类模型在生成实际内容之前会先输出“思考” token。

推理模型对用户可见的响应延迟并不是首 token 时间，而是首个非思考 token 的时间。

我们维护着一个30 轮对话基准测试，用于在具有挑战性的真实语音智能体场景中测试 LLM 的性能。

我们饶有兴致地跟踪了最近的两个趋势。

从 2025 年底开始，新模型开始在这一基准测试上达到饱和。然而，所有这些新模型对语音用例来说都太慢了。要将一个模型用于实时语音对话，我们需要 TTFT（首个非思考 token）快于 700 毫秒。尽管如此，能在这一高难度基准测试上达到饱和仍是一个重大里程碑。

今年，我们看到开放模型出现了新的性能跃升。Nemotron 3 Ultra 是第一个在这一基准测试上取得 100% 得分的开放模型。它也是第一个——无论开源还是专有——既能让基准测试饱和、又能提供低于 700 毫秒 TTFT 的模型。

如今基准测试图表上有两条帕累托前沿。Nemotron 3 Ultra（自托管）、Kimi 2.6（托管于 Cerebras）和 Gemma 4 31b（托管于 Lilac）构成了开放模型的帕累托前沿。GPT-4.1、Claude Haiku 4.5 和 Claude Sonnet 5.6 则构成了另一条专有模型/第一方 API 的前沿。

在延迟敏感的用例中，开放模型的表现优于闭源模型。

这里的注意事项是，你必须自托管，或者向 Cerebras、Lilac 这样的新平台承诺可观的推理用量。另一方面，使用开放模型也带来了微调和定制的其他机会。

5.4.2 LLM提示词帮助

大部分的转录错误源于转录模型在实时流中可获得的上下文非常少。

如今的 LLM 已足够聪明，能绕开转录错误。LLM 在执行推理时可以访问完整的对话上下文。因此你可以告诉 LLM，输入是用户语音的转录文本，并让它依此进行推理。

You are a helpful, concise, and reliable voice assistant. Your primary goal is to understand the user's spoken requests, even if the speech-to-text transcription contains errors. Your responses will be converted to speech using a text-to-speech system. Therefore, your output must be plain, unformatted text.

When you receive a transcribed user request:
1. Silently correct for likely transcription errors. Focus on the intended meaning, not the literal text. If a word sounds like another word in the given context, infer and correct. For example, if the transcription says "buy milk two tomorrow" interpret this as "buy milk tomorrow".
2. Provide short, direct answers unless the user explicitly asks for a more detailed response. For example, if the user says "what time is it?" you should respond with "It is 2:38 AM". If the user asks "Tell me a joke", you should provide a short joke.
3. Always prioritize clarity and accuracy. Respond in plain text, without any formatting, bullet points, or extra conversational filler.
4. If you are asked a question that is time dependent, use the current date, which is February 3, 2025, to provide the most up to date information.
5. If you do not understand the user request, respond with "I'm sorry, I didn't understand that."

Your output will be directly converted to speech, so your response should be natural-sounding and appropriate for a spoken conversation.

5.6. 音频处理

优秀的语音 AI 平台或库大多会隐藏音频采集与处理的复杂性。但如果你在构建复杂的语音智能体，迟早会遇到音频处理中的 bug 和边界情况。[19] 因此，快速了解一遍音频输入流水线是值得的。

[19] ……这一点可以推广到软件中的所有事物，乃至生活中的大多数事情。

5.6.1 麦克风与自动增益控制

如今的麦克风是极其精密的硬件设备，并配套了大量底层软件。这通常很棒——我们从移动设备、笔记本电脑和蓝牙耳机内置的微型麦克风中就能获得极佳的音频。

但有时这些底层软件并不按我们的意愿工作。特别是，蓝牙设备可能给语音输入增加数百毫秒的延迟。作为语音 AI 开发者，这在很大程度上是你无法控制的。但值得意识到的是，因特定用户所使用的操作系统和输入设备，延迟会有很大差异。

大多数音频采集流水线都会对输入信号施加一定程度的自动增益控制。同样，这通常正是你想要的，因为它可以补偿用户与麦克风之间的距离等因素。你往往可以禁用部分自动增益控制，但在消费级设备上通常无法完全禁用。

5.6.2 回声消除

如果用户把手机贴在耳边，或者戴着耳机，你就不必担心本地麦克风与扬声器之间的反馈。但如果用户要使用免提通话，或者不戴耳机使用笔记本电脑，那么良好的回声消除就极其重要。

回声消除对延迟非常敏感，因此必须在设备端（而非云端）运行。如今，出色的回声消除已内置于电话栈、Web 浏览器和 WebRTC 原生移动 SDK 中。[20]

因此，如果你使用语音 AI、WebRTC 或电话 SDK，你应该拥有在几乎所有真实场景中都可“开箱即用”的可靠回声消除。如果你在自行搭建语音 AI 采集流水线，就需要弄清楚如何集成回声消除逻辑。例如，如果你在构建一个基于 WebSocket 的 React Native 应用，默认情况下不会有任何回声消除。[21]

[20] 请注意，Firefox 的回声消除效果不太好。我们建议语音 AI 开发者以 Chrome 和 Safari 作为主要平台进行开发，仅在时间允许的情况下把 Firefox 作为次要平台进行测试。

[21] 我们最近帮助一位开发者调试其 React Native 应用的音频问题。根本原因是他们没有意识到需要自行实现回声消除，因为他们并未使用语音 AI 或 WebRTC SDK。

5.6.3 噪声抑制、语音与音乐

电话和 WebRTC 的音频采集流水线几乎总是默认使用“语音模式”。语音可以比音乐压缩得多，而且降噪和回声消除算法在较窄带信号上更容易实现。

许多电话平台只支持 8kHz 音频。以现代标准来看，这明显是低质量的。如果你的音频流经具有这一限制的系统，那你也无能为力。用户可能会注意到音质问题，也可能不会——大多数人对电话通话音质的期望并不高。

WebRTC 支持非常高质量的音频。[22] WebRTC 的默认设置通常是 48kHz 采样率、单声道、32 kbps Opus 编码，以及中等强度的噪声抑制算法。这些设置针对语音进行了优化，适用于各种设备和环境，通常是语音 AI 的正确选择。

但在这些设置下，音乐听起来不会好！

如果你需要通过 WebRTC 连接传输音乐，你需要：

  • 关闭回声消除（用户需要佩戴耳机）。
  • 关闭噪声抑制。
  • 可选地，启用立体声。
  • 提高 Opus 编码比特率（单声道的理想目标是 64 kbps，立体声为 96 kbps 或 128 kbps）。

[22] 高质量音频的一些用例：

  • 由 LLM 担任教师的音乐课。
  • 录制包含背景音或音乐的播客。
  • 交互式生成 AI 音乐。

在这三种选择中，Opus 显然是最好的。Opus 已内置于 Web 浏览器中，从一开始就被设计为低延迟编解码器，而且非常高效。它在很宽的比特率范围内都表现良好，并且同时支持语音和高保真用例。

16 位 PCM 就是“原始音频”。你可以将 PCM 音频帧直接发送到软件声音通道（前提是采样率和数据类型被正确指定）。但请注意，这种未压缩音频通常不适合通过互联网传输。24kHz PCM 的比特率为 384 kbps。这一比特率相当大，许多来自终端用户设备的真实网络连接都难以实时传输这些数据。

5.6.5 服务器端噪声处理与说话人分离

语音转文本和语音活动检测模型通常可以忽略一般的环境噪声——街道声音、狗叫、靠近麦克风的响亮风扇声、键盘敲击声。因此，对于许多人与人通话场景至关重要的传统“噪声抑制”算法，对语音 AI 来说并不那么关键。

但有一种音频处理对语音 AI 特别有价值：主说话人分离。主说话人分离会抑制背景人声，这可以显著提升转录准确率。

或者想象一个用户待在客厅里，背景中开着电视或收音机。由于人类通常很擅长过滤掉低音量背景人声，人们在拨打客服热线之前未必会想到关掉电视或收音机。

5.7. 网络传输

5.7.1 WebSockets 与 WebRTC

WebSockets 和 WebRTC 都被 AI 服务用于音频流传输。

WebSockets 非常适合服务器到服务器的场景。对于延迟不是首要考虑因素的场景，它们也够用了，而且很适合原型开发和一般性的技术尝试。

但在生产环境中，不应将 WebSockets 用于客户端-服务器的实时媒体连接。

如果你在构建浏览器或原生移动应用，并且对话级延迟对你的应用很重要，那么你应该使用 WebRTC 来收发应用音频。

在与终端用户设备之间进行实时媒体传输时，WebSockets 存在的主要问题有：

  • WebSockets 构建在 TCP 之上，因此音频流会受到队头阻塞的影响。
  • WebRTC 使用的 Opus 音频编解码器与 WebRTC 的带宽估计和包速率控制（拥塞控制）逻辑紧密耦合，使得 WebRTC 音频流能够抵御各种真实网络行为——而这些行为会导致 WebSocket 连接不断累积延迟。
  • Opus 音频编解码器具有非常好的前向纠错能力，使音频流能够抵御相对较高的丢包率。（不过，只有当网络传输能丢弃迟到数据包且不发生队头阻塞时，这才有用。）
  • WebRTC 音频会自动打上时间戳，因此播放和打断逻辑都变得非常简单。
  • WebRTC 内置了用于详细性能和媒体质量统计的钩子。优秀的 WebRTC 平台会为你提供详细的仪表盘和分析。用WebSocket构建如此级别的可观察性极其困难，甚至几乎不可能。
  • WebSocket 的重连逻辑很难做到健壮。你必须构建一套 ping/ack 框架（或者充分测试并理解你的 WebSocket 库所提供的框架）。TCP 超时和连接事件在不同平台上的行为各不相同。
  • 最后，如今优秀的 WebRTC 实现都自带非常好的回声消除、降噪和自动增益控制。

你有两种方式使用 WebRTC。

  1. 通过云端的 WebRTC 服务器进行路由。
  2. 客户端设备与语音 AI 进程之间建立直连。

对于许多真实用例，通过云服务器路由的表现会更好（参见下文的网络路由）。云基础设施还实现了一些直连难以同样轻松或可扩展地实现的功能（多方会话、与电话系统集成、录制）。

但“无服务器”WebRTC 很适合许多语音 AI 用例。Pipecat 通过 SmallWebRTCTransport 类支持无服务器 WebRTC。而像 Hugging Face 的 FastRTC 这样的框架，则是完全围绕这种网络模式构建。

5.7.2 HTTP

HTTP 对语音 AI 来说依然有用且重要！HTTP 是互联网上服务互联的通用语言。REST API 是 HTTP，Webhook 也是 HTTP。

面向文本的推理也是通过 HTTP 进行的，因此语音 AI 流水线通常会调用 HTTP API 来完成对话循环中的 LLM 部分。

语音智能体在与外部服务和内部 API 集成时也会使用 HTTP。一个有用的技巧是将 LLM 的函数调用代理到 HTTP 端点。这样就把语音 AI 智能体的代码和运维与函数实现解耦了。

多模态 AI 应用往往需要同时实现 HTTP 和 WebRTC 两条代码路径。想象一个同时支持文本模式和语音模式的聊天应用。对话状态需要能够通过任一条连接路径访问，这对客户端和服务器端代码都有影响（例如 Kubernetes pod 和 Docker 容器等组件的架构设计方式）。

HTTP 的两个缺点是延迟，以及实现长连接双向通信的困难。

  • 建立加密的 HTTP 连接需要多次网络往返。要让媒体连接的建立时间远低于 30 毫秒是相当困难的，即使对于高度优化的服务器，实际的首字节发送时间也接近 100 毫秒。
  • 长连接、双向的 HTTP 连接管理起来相当困难，通常你还是直接使用 WebSockets 更好。
  • HTTP 是基于 TCP 的协议，因此影响 WebSockets 的同样队头阻塞问题也会影响 HTTP。
  • 通过 HTTP 发送原始二进制数据并不常见，因此大多数 API 选择对二进制数据进行 base64 编码，而这会增加媒体流的比特率。

这就引出了 QUIC……

一个同时使用 HTTP 和 WebRTC 进行网络通信的语音 AI 智能体。

5.7.3 QUIC 与 MoQ

QUIC 是一种新的网络协议，被设计为最新版本 HTTP（HTTP/3）的传输层——同时也灵活支持其他互联网规模的用例。

QUIC 是基于 UDP 的协议，解决了上述 HTTP 的所有问题。使用 QUIC，你可以获得更快的连接时间、双向流以及无队头阻塞。Google 和 Facebook 一直在稳步推进 QUIC 的部署，因此如今你的部分 HTTP 请求是以 UDP（而非 TCP）数据包的形式穿越互联网的。[24]

[24] 如果你在互联网上构建东西已经很久了，这多少有点🤯。HTTP 一直是一种基于 TCP 的协议！

QUIC 将成为互联网媒体流传输未来的重要组成部分。不过，实时媒体流传输向基于 QUIC 的协议迁移需要时间。构建基于 QUIC 的语音智能体的一个阻碍是，Safari 对 WebSockets 基于 QUIC 的演进版本 WebTransport 的支持还非常新。

Media over QUIC IETF 工作组[25]的目标是制定一套“用于媒体摄取与分发的简单低延迟媒体传输方案”。与所有标准一样，要弄清楚如何用尽可能简单的构建块，支持尽可能广泛的重要用例并非易事。人们对将 QUIC 用于点播视频流、大规模视频广播、直播视频流、大量参与者的低延迟会话以及低延迟一对一会话感到兴奋。

[25] IETF Media Over QUIC 工作组

实时语音 AI 用例的增长时机恰到好处，足以影响 MoQ 标准的发展。

5.7.4 网络路由

无论底层网络协议是什么，长距离网络连接在延迟和实时媒体可靠性方面都会带来问题。

对于实时媒体传输，你希望服务器尽可能靠近用户。

例如，从英国用户到托管在 AWS us-west-1（北加州）的服务器的数据包往返时间通常约为 140 毫秒。相比之下，同一用户到 AWS eu-west-2 的 RTT 通常在 15 毫秒或更低。

英国用户到 AWS us-west-1 的 RTT 比到 AWS eu-west-2 多约 100 毫秒

这超过了 100 毫秒的差异——如果你的语音到语音延迟目标是 1000 毫秒，这就相当于延迟“预算”的百分之十。

边缘路由

你可能无法在靠近所有用户的地方部署服务器。

要实现全球用户 15 毫秒的 RTT，至少需要部署到 40 个全球数据中心。这是一项庞大的运维工作。而且如果你在运行需要 GPU 的工作负载，或者依赖本身并未全球部署的服务，这可能根本无法实现。

你无法欺骗光速。[26] 但你可以设法避免路由的波动和拥塞。

[26] 源自网络工程师的古老智慧——编者注。

关键在于让公共互联网路由尽可能短。把用户连接到离他们最近的边缘服务器，然后从那里使用私有路由。

这种边缘路由可以降低数据包 RTT 的中位数。英国→北加州经由私有骨干网的路由很可能约为 100 毫秒。100 毫秒（长距离私有路由）+ 15 毫秒（公共互联网上的第一跳）= 115 毫秒。这一私有路由的 RTT 中位数比公共路由的 RTT 中位数好 25 毫秒。

从英国到 AWS us-west-1 的边缘路由。公共网络上的第一跳 RTT 仍为 15 毫秒。但经由私有网络到北加州的长距离路由 RTT 为 100 毫秒。总计 115 毫秒的 RTT 比从英国到 us-west-1 的公共路由快 25 毫秒。它的波动也明显更小（丢包更少、抖动更低）。

不过，比 RTT 中位数的改善更为关键的是传输可靠性的提升和抖动的降低。[27] 私有路由的 P95 RTT 会显著低于公共路由的 P95。[28]

这意味着，经由长距离公共路由的实时媒体连接会比使用私有路由的连接明显更卡顿。回想一下，我们要尽可能快地传输每个音频数据包，但又必须按顺序播放这些数据包。单个延迟的数据包就会迫使我们扩大抖动缓冲区，保留其他已收到的数据包，直到那个延迟的数据包到达。（或者，直到我们判定等待时间过长，然后用高明的算法或有毛刺的音频样本来填补空缺。）

[27] 抖动是指数据包穿越路由所需时间的波动程度。

[28] P95 是某项指标的第 95 百分位测量值。P50 是中位数测量值（第 50 百分位）。粗略地说，我们把 P50 视为平均情况，把 P95 视为对“典型最坏情况”连接的大致刻画。

抖动缓冲区——更大的抖动缓冲区会直接导致用户感知到的音视频延迟更大。让抖动缓冲区尽可能小，对良好用户体验的贡献非常显著。

优秀的 WebRTC 基础设施服务商都会提供边缘路由。他们能够向你展示服务器集群的分布位置，并提供体现其私有路由性能的指标。

5.8. 轮次检测

轮次检测 是指判断用户何时说完话并期望 LLM 作出回应。

我们（人类）每次与他人交谈时都在做轮次检测。[29]

[29] 而且我们并不总是判断正确！尤其是在没有视觉线索辅助，或者音频传输存在延迟的情况。

对于“从零”构建（不使用 Pipecat 这类框架）的语音智能体，最常见的抱怨就是智能体打断得太频繁。但这在很大程度上是一个已被解决的问题。采用当今最佳轮次检测方法的语音智能体响应迅速，打断的准确度与真人非常接近。

在学术文献中，轮次检测的各个方面被称为短语检测、语音分割和端点检测。（关于这一主题存在学术文献这一事实，本身就说明它不是一个简单的问题。）

如果你只想阅读最佳实践概述，可以直接跳到最先进的轮次检测。在接下来的几节中，我们将逐一介绍轮次检测的各个构建模块。

5.8.1 语音活动检测

为语音 AI 智能体做轮次检测的一种常见方式是，假定长时间的停顿意味着用户已经说完话。

语音 AI 智能体流水线使用一个小型的专用语音活动检测模型来识别停顿。VAD 模型经过训练，能够将音频片段分类为语音或非语音。（这比仅根据音量水平来识别停顿要健壮得多。）

可以在客户端或服务器上运行 VAD。如果无论如何都需要在客户端进行大量音频处理，那么可能需要在客户端上运行 VAD。例如，你可能在嵌入式设备上识别唤醒词，只有在检测到短语开头有唤醒词时才通过网络发送音频。嘿，Siri……

不过，更简单、通用的做法是把 VAD 作为语音 AI 智能体处理循环的一部分来运行。如果你的用户是通过电话连接的，你就没有可运行 VAD 的客户端，因此必须在服务器端完成。

语音 AI 中最常用的 VAD 模型是 Silero VAD。这个开源模型在 CPU 上运行高效，支持多种语言，对 8kHz 和 16kHz 音频都有良好表现，并且提供可在 Web 浏览器中使用的 wasm 包。在实时单声道音频流上运行 Silero 通常只需占用典型虚拟机 CPU 核心的不到 1/8。

轮次检测算法会有几个配置参数：

  • 判定轮次结束所需的停顿长度。
  • 触发开始说话事件所需的语音片段长度。
  • 将每个音频片段分类为语音的置信度水平。
  • 语音片段的最低音量。

如果你单独使用 VAD 进行轮次检测，下面是 Pipecat 中这四个 VAD 配置参数的名称和默认值。（但如今你不应该单独使用 VAD。参见下文的最先进的轮次检测。）

一个语音活动检测处理步骤，此处被配置为在语音转文本之前运行


  VAD_STOP_SECS = 0.8
  VAD_START_SECS = 0.2
  VAD_CONFIDENCE = 0.7
  VAD_MIN_VOLUME = 0.6

调优这些参数可以改善特定用例下的轮次检测行为。

5.8.2 按下说话

基于语音停顿进行轮次检测的明显问题是，人们有时会停顿，但并没有说完。

个人的说话风格各不相同。在某些类型的对话中，人们会比在其他对话中停顿得更多。

设置较长的停顿间隔会造成生硬的对话——这是非常糟糕的用户体验。但如果停顿间隔较短，语音智能体就会频繁打断用户——这同样是糟糕的用户体验。

基于停顿的轮次检测最常见的替代方案是按下说话。按下说话意味着要求用户在开始说话时按下或按住按钮，说完后再次按下按钮或松开。（想想老式对讲机是怎么工作的。）

使用按下说话时，轮次检测没有歧义。听写程序和编程智能体的语音集成常常使用按下说话。缺点是按下说话的用户体验与自然对话相去甚远。此外，电话语音 AI 智能体无法使用按下说话。

5.8.3 结束标记

你也可以使用特定词语作为轮次结束标记。（想想卡车司机用民用波段对讲机通话时说的“over”（完毕）。

识别特定结束标记最简单的方法是对每个转录片段运行正则表达式匹配。但你也可以使用小型语言模型来检测结束词或短语。

使用显式结束标记的语音 AI 应用并不常见。用户必须学会如何与这些应用交谈。但对于专门的用例，这种方法可能非常有效。

例如，去年我们看到一个很棒的演示：某位开发者作为业余项目为自己构建的写作助手。他们使用各种命令短语来指示轮次结束并在不同模式之间切换。

5.8.4 上下文感知的轮次检测（语义 VAD 与 smart turn）

人类做轮次检测时会使用多种线索：

  • 识别出像“um”这样的填充词很可能表示说话还会继续。
  • 语法结构。
  • 对模式的认知，例如电话号码有特定的位数。
  • 语调和发音模式，比如在停顿前拖长最后一个词。

深度学习模型非常擅长识别模式。小型的专用分类模型可以基于语言、语调和发音模式进行训练。

现在已有多个不错的轮次检测模型可用，而且领先的 STT 模型服务商都在将轮次检测集成到他们的 STT API 中。

Pipecat Smart Turn 是一个完全开源的、基于原生音频的轮次检测模型，支持 23 种语言。

Smart Turn模型由VAD设置为非常短的静默间隔进行门控，并与转录并行执行。这一设计带来了许多有用的特性：

  • 该模型直接作用于用户的语音音频，因此它同时考虑语言层面的模式和音频层面的模式，例如语调、语速和发音。
  • 由于 Smart Turn 不处理文本，它不必等待转录完成。这使得延迟尽可能低。
  • 该模型很小，经过优化，可在典型云 vCPU 上约 30 毫秒内给出分类结果（轮次完整或不完整）。

所有这些加起来意味着，从用户说话停顿时算起，我们大约在 250 毫秒内就能做出轮次判断。

拥有极其稳定的 250 毫秒轮次分类，有助于我们设计、调试和监控智能体的行为。机器学习模型通常是“黑盒”，难以调试。但我们的流水线不是黑盒。我们可以看到每个组件的运行情况。

Pipecat Smart Turn 的所有训练数据、训练代码和评估/基准测试代码都可以在 GitHub 和 HuggingFace 上免费获取。该模型采用 BSD 开源许可证授权。许多团队贡献了数据以改进该模型。如果你想贡献并参与 Smart Turn 的开发，请提交 PR 或加入 Pipecat Discord。

5.8.5 最先进的轮次检测：VAD、Smart Turn 与 LLM 单 token 标记

当今最好的轮次检测结合了三层处理：

  1. 语音活动检测，使用较短（200 毫秒）的触发阈值。
  2. 一个小型、快速、可在 CPU 上运行的原生音频轮次检测模型。该模型能够捕捉到诸如语调变化和填充音等不会被转录出来的音频细节。
  3. 用于对话 LLM 的提示词混入（prompt mixin），做出可配置的、上下文感知的轮次完成判断。

这些都不是新事物。我们使用 VAD 已经很久了。我们在 2024 年 12 月训练了 Pipecat Smart Turn 原生音频模型的第一个版本。而基于提示词的大模型轮次检测（有时称为“选择性拒绝”），我们已经实验了一年多。

如今到了 2026 年，Smart Turn 模型和我们在语音智能体中使用的最先进 LLM 都已变得足够出色，将它们结合使用让人感觉我们终于“解决”了轮次检测问题。

The insight here is，我们可以把音频轮次检测模型对音频语音模式的快速“过滤”，与 LLM 对完整对话上下文的访问及其对文本对话模式的理解结合起来。

使用单 token 标记是让这一方案在生产环境中奏效的关键。单 token 标记是指要求 LLM 始终在响应的开头输出一个用于轮次检测的分类字符。我们用这个字符来判断用户轮次是否完整（并将其过滤掉，它不会成为 LLM 输出的一部分，进而不会传给文本转语音服务和其他下游流水线组件）。

对于标记，你可以使用任何能映射为单个 token 的字符串。下面是 Pipecat FilterIncompleteUserTurnStrategies 服务所使用的 token。

  • ✓ 表示智能体应正常（立即）回应
  • ○ 表示“短不完整”——智能体应等待 5 秒
  • ◐ 表示“长不完整”——智能体应等待 10 秒

LLM 在做出轮次检测判断时拥有完整的对话上下文。因此 LLM 可以做到这样的事情：当用户在电话号码中间停顿时生成 ○ 标记（短不完整），而当用户在电话号码结尾停顿时生成 ✓ 标记。这效果非常好，如果你习惯了纯粹基于 VAD 的轮次检测，第一次遇到时简直像魔法一样。请注意，你通常需要向提示词混入中添加具体示例，以调优这类行为。（电话号码在不同国家有不同的格式！）完整的 Pipecat 文档见此处。

下面是 FilterIncompleteUserTurnStrategies 服务的默认提示词混入的开头部分。完整的混入内容有 480 个单词，并针对 GPT、Claude 和 Gemini 模型进行了大量测试。你可以针对自己的用例进行调整，也可以配置短等待和长等待。而且，如果你想进一步发展这一策略，可以自定义决策框架，以不同方式使用来自 VAD、Smart Turn 和 LLM 的信号，或者添加额外的信号，例如处理用户视频画面的计算机视觉信号。

5.9. 打断处理

打断处理是指允许用户打断语音 AI 智能体。打断是对话的正常组成部分，因此优雅地处理打断很重要。

要实现打断处理，你需要流水线的每个部分都可取消。你还需要能够非常快速地停止客户端上的音频播放。

通常，你所使用的框架会在触发打断时负责停止所有处理。但如果你直接使用一个以快于实时的速度向你发送原始音频帧的 API，你就必须手动停止播放并清空音频缓冲区。

5.9.1 避免误打断

有几种非预期打断的来源值得注意。

  1. 被分类为语音的瞬时噪声。优秀的 VAD 模型在区分语音与“噪声”方面做得非常好。但某些短促、尖锐的起始音频，如果出现在话语开头，会被赋予中等的语音置信度。咳嗽声和键盘敲击声都属于这一类。你可以调整 VAD 的起始片段长度和置信度水平，以尽量减少这种打断来源。代价是，延长起始片段长度并提高置信度阈值，会给你确实希望检测为完整话语的极短短语带来问题。[31]
  2. 回声消除失效。回声消除算法并不完美。从静音到语音播放的转换尤其具有挑战性。如果你做过大量语音智能体测试，你可能听到过机器人在刚开始说话时就打断了自己。罪魁祸首是回声消除让少量起始语音音频反馈回了麦克风。VAD 的最小起始片段长度有助于避免这个问题。对音频音量水平应用指数平滑[32]以避免音量突变，同样有帮助。
  3. 背景人声。VAD 模型不会区分用户语音和背景人声。如果背景人声比你的音量阈值更响，就会触发打断。说话人分离的音频处理步骤可以减少由背景人声引起的误打断。参见上文服务器端噪声处理与说话人分离一节中的讨论。

5.9.2 打断后保持准确的上下文

由于 LLM 生成输出的速度快于实时，当打断发生时，你往往会有一批待发送给用户的 LLM 输出排在队列中。

通常，你希望对话上下文与用户实际听到的内容一致（而不是你的流水线以快于实时的速度生成的内容）。

你可能还会以文本形式保存对话上下文。[33]

所以你需要一种方法来弄清楚用户实际听到了哪些文本！

最好的语音转文本服务能够报告词级时间戳数据。利用这些词级时间戳来缓冲并组装与用户所听音频相匹配的助手消息文本。参见上文文本转语音一节中关于词级时间戳的讨论。Pipecat 会自动处理这一点。

[31] Pipecat 的标准流水线配置结合了 VAD 和转录事件，以尽量避免误打断和漏检话语这两种情况。

[32] Pipecat VAD 输入音频指数平滑代码

[33] 标准的上下文结构是 OpenAI 制定的用户/助手消息列表格式。

5.10. 管理对话上下文

LLM 是无状态的。这意味着对于多轮对话，每次生成新响应时，你都需要把之前所有的用户和智能体消息——以及其他配置元素——重新输入给 LLM。

Turn 1:
  User: What's the capital of France?
  LLM: The capital of France is Paris.

Turn 2:
  User: What's the capital of France?
  LLM: The capital of France is Paris.
  User: Is the Eiffel Tower there?
  LLM: Yes, the Eiffel Tower is in Paris.
  
Turn 3:
  User: What's the capital of France?
  LLM: The capital of France is Paris.
  User: Is the Eiffel Tower there?
  LLM: Yes, the Eiffel Tower is in Paris.
  User: How tall is it?
  LLM: The Eiffel Tower is about 330 meters tall.

每一轮都将完整的对话历史发送给 LLM。

对于每次推理操作——也就是每一轮对话——你可以向 LLM 发送：

  • 系统指令
  • 对话消息
  • 供 LLM 使用的工具（函数）
  • 配置参数（例如 temperature）

5.10.1 LLM API 之间的差异

这一总体设计在当今所有主流 LLM 中都是一样的。

但各家服务商的 API 之间存在差异。OpenAI、Google 和 Anthropic 都有各自不同的消息格式，工具/函数定义的结构也不同，指定系统指令的方式也不同。

有一些第三方 API 网关和软件库会把 API 调用翻译成 OpenAI 的格式。这很有价值，因为能够在不同 LLM 之间切换是有用的。但这些服务并不总能恰当地把差异抽象掉。新特性以及各家 API 独有的特性并不总能得到支持。（而且翻译层有时还会有 bug。）

抽象还是不抽象，这仍然是一个问题——在 AI 工程尚处相对早期的今天尤其如此。[34]

例如，Pipecat 会为上下文消息和工具定义双向转换 OpenAI 格式的消息。但是否应该这样做以及如何做，曾是社区激烈讨论的话题！[35]

5.10.2 在轮次之间修改上下文

必须管理多轮上下文增加了开发语音 AI 智能体的复杂性。另一方面，回溯性地修改上下文可能很有用。对于每一轮对话，你都可以精确决定向 LLM 发送什么内容。

LLM 并不总是需要完整的对话上下文。缩短或摘要上下文可以降低延迟、减少成本，并提升语音 AI 智能体的可靠性。关于这一主题的更多内容，参见下文的脚本化与指令遵循一节。

5.11. 函数调用

生产环境中的语音 AI 智能体高度依赖 LLM 函数调用。

函数调用用于：

  • 为检索增强生成获取信息。
  • 与现有的后端系统和 API 交互。
  • 与电话技术栈集成——呼叫转接、排队、发送 DTMF 音。
  • 脚本遵循——实现工作流状态转换的函数调用。

5.11.1 语音 AI 场景下函数调用的可靠性

随着语音 AI 智能体被部署到越来越复杂的用例中，可靠的函数调用变得越来越重要。

最先进的 LLM 在函数调用方面正稳步提升，但语音 AI 用例往往把 LLM 的函数调用能力推到极限。

语音 AI 智能体往往会：

  • 在多轮对话中使用函数。在多轮对话中，随着每一轮都添加用户和助手消息，提示词会变得越来越复杂。这种提示词复杂性会削弱 LLM 的函数调用能力。
  • 定义多个函数。一个语音 AI 工作流通常需要五个或更多函数。
  • 在一次会话中多次调用函数。

我们对所有主要的 AI 模型发布都进行了大量测试，并经常与训练这些模型的人交流。很明显，上述所有特征相对于用来训练当代 LLM 的数据而言，都有些偏离分布。

这意味着，即使当代 LLM 在通用函数调用基准测试上表现良好，它们在语音 AI 用例上仍会遇到困难。不同的 LLM、同一模型的不同更新版本，在函数调用上的擅长程度各不相同；在不同情境下，对不同类型的函数调用的擅长程度也各不相同。

如果你在构建语音 AI 智能体，那么开发自己的评测(Evals)来测试应用的函数调用性能就非常重要。参见下文的语音 AI 评测一节。

5.11.2 函数调用延迟

函数调用会增加延迟——可能增加很多延迟——原因有四个：

  1. 当 LLM 判断需要调用函数时，它会输出一条函数调用请求消息。你的代码随后针对所请求的特定函数执行相应操作，然后带着相同的上下文再加上一条函数调用结果消息再次调用推理。因此，每次调用函数，你都需要进行两次推理调用而非一次。
  2. 函数调用请求无法流式处理。我们需要拿到完整的函数调用请求消息，才能执行函数调用。
  3. 在提示词中添加函数定义会增加延迟。这一点有些模糊不清；最好能开发面向延迟的评测，专门衡量在提示词中添加函数定义所带来的额外延迟。但很明显，有些 API 至少在部分时间里，一旦启用工具使用，TTFT 中位数就会升高，无论函数是否真的被调用。
  4. 你的函数可能很慢！如果你在对接一个遗留后端系统，你的函数可能需要很长时间才能返回。

每次用户说完话后，你都需要相当快地给出音频反馈。如果你知道函数调用可能需要很长时间才能返回，你大概会希望输出语音，告诉用户正在发生什么并请他们稍等。

包含函数调用的推理的 TTFT。LLM 的 TTFT 为 450 毫秒，吞吐量为每秒 100 token。如果函数调用请求分块为 100 token，那么输出该请求需要 1 秒。然后我们执行函数并再次运行推理。这一次我们可以流式获取输出，因此 450 毫秒后就能拿到可用的首批 token。整个推理的 TTFT 为 1450 毫秒（不包括执行函数本身所需的时间）。

你可以选择：

  • 总是在执行函数调用之前输出一条消息。“请稍候，我正在为您办理 X……”
  • 设置一个看门狗定时器，只有当函数调用循环在定时器触发前尚未完成时才输出消息。“还在处理中，请再稍等片刻……”

当然，也可以两者兼用。而且你可以在执行长时间运行的函数调用时播放背景音乐。[36]

[36] 不过拜托，别放《Jeopardy》的主题曲。

5.11.3 处理打断

LLM 在训练时期望函数调用请求消息和函数调用响应消息是成对出现的。

这意味着：

  1. 你需要暂停语音到语音的推理循环，直到所有函数调用完成。关于异步函数调用的说明见下文。
  2. 如果一个函数调用被打断且永远不会完成，你需要向上下文中放入一条函数调用响应消息，用以表明……某种情况。

这里的规则是：如果 LLM 调用了函数，你就需要在上下文中放入一对请求/响应消息。

  • 如果你在上下文中放入一条悬空的函数调用请求消息，然后继续多轮对话，你就制造了一个与 LLM 训练方式相背离的上下文。（有些 API 不允许这样做。）
  • 如果你根本不向上下文中放入请求/响应对，你就是在（通过上下文内学习）教 LLM 不要调用该函数。[37] 同样，结果不可预测，而且很可能不是你想要的。

[37] 参见论文 Language Models are Few-Shot Learners。

Pipecat 会在每次发起函数调用时向上下文中插入一对请求/响应消息，帮助你遵循这些上下文管理规则。（当然，你可以覆盖这一行为，直接管理函数调用的上下文消息。）

下面展示了两种不同配置方式（运行至完成和可打断）下函数调用的模式。

User:  Please look up the price of 1000 widgets.
LLM: Please wait while I look up the price for 1000 widgets. 
function call request: { name: "price_lookup", args: { item: "widget", quantity: 1000 } }
function call response: { status: IN_PROGRESS }

初始上下文消息。一条函数调用请求消息和一个函数调用响应占位符。

User:  Please look up the price of 1000 widgets.
function call request: { name: "price_lookup", args: { item: "widget", quantity: 1000 } }
function call response: { result: { price: 12.35 } }

函数调用完成时的上下文。

User:  Please look up the price of 1000 widgets.
LLM: Please wait while I look up the price for 1000 widgets. 
function call request: { name: "price_lookup", args: { item: "widget", quantity: 1000 } }
function call response: { status: IN_PROGRESS }

User: Please lookup the price of 1000 pre-assembled modules.
LLM: Please wait while I also look up the price for 1000 pre-assembled modules. 
function call request: { name: "price_lookup", args: { item: "pre_assembled_module", quantity: 1000 } }
function call response: { status: IN_PROGRESS }

占位符让对话能够在函数调用运行期间继续进行，而不会“迷惑”LLM。

User:  "Please look up the price of 1000 widgets."
LLM: "Please wait while I look up the price for 1000 widgets." 
function call request: { name: "price_lookup", args: { item: "widget", quantity: 1000 } }
function call response: { status: CANCELLED }

User: Please lookup the price of 1000 pre-assembled modules.
LLM: Please wait while I look up the price for 1000 pre-assembled modules.
function call request: { name: "price_lookup", args: { item: "pre_assembled_module", quantity: 1000 } }
function call response: { status: IN_PROGRESS }

如果函数调用被配置为可打断，那么当用户在函数调用进行期间说话时，该调用将被取消。

5.11.4 流式模式与函数调用分块

在语音 AI 智能体代码中，你几乎总是以流式模式执行对话推理调用。这能让你尽快拿到最初几个内容分块，这对语音到语音的响应延迟很重要。

不过，流式模式与函数调用是一对别扭的组合。流式处理对函数调用分块没有帮助。在拼装出 LLM 完整的函数调用请求消息之前，你无法调用函数。[38]

[38] 如果你在使用 AI 框架，框架很可能已经为你隐藏了这种复杂性。

在推理服务商持续演进其 API 的过程中，这里有一些反馈：请提供一种以原子方式交付函数调用分块、并与任何流式内容分块相隔离的模式。这将显著降低使用 LLM 服务商 API 的代码复杂度。

5.11.5 如何以及在何处执行函数调用

当 LLM 发出函数调用请求时，你该怎么做？以下是一些常用模式：

  • 直接在你的代码中执行一个与所请求函数同名的函数调用。这几乎是所有 LLM 函数调用文档示例中都能看到的做法。
  • 根据参数和上下文把请求映射到某个操作。可以把它理解为让 LLM 发起一个泛化的函数调用，而由你在代码中消除歧义。这种模式的优势在于，如果你只给 LLM 少量可选函数，它们的函数调用表现通常更好。[39]
  • 把函数调用代理到客户端。在应用（而非电话）场景中你可以使用这种模式。例如，想象一个 get_location() 函数。你想获取用户设备的当前位置，因此需要接入该设备上的地理位置查询 API。
  • 把函数调用代理到网络端点。这在企业场景中往往是一个特别有用的模式。定义一组与内部 API 交互的函数，然后在代码中创建一个抽象层，把这些函数调用作为 HTTP 请求执行。

[39] 在这里，请把函数调用理解为一个宽泛的类别——是形式意义上的函数，而非口语意义上的。你可以从查找表中返回一个值，也可以运行一条 SQL 查询。

函数调用模式

5.11.6 异步函数调用

有时你并不希望函数调用立即返回。你知道函数需要花费不可预测的长时间才能完成，也许它根本不会完成。甚至你可能想启动一个长时间运行的进程，让它随时间以开放的方式不断向上下文中添加内容。

想象一个步行导览应用，它允许用户表达自己对游览途中可能看到的事物的兴趣。“如果我们路过著名作家曾居住过的地方，我特别想听听相关的介绍。”对此一个不错的架构是：每当用户表达某个具体兴趣时，LLM 就调用一个函数。该函数会启动一个后台进程，在发现与该兴趣相关的任何内容时把信息注入上下文。

如今你无法直接用 LLM 函数调用做到这一点。函数调用的请求/响应消息必须在上下文中成对出现。

所以，与其定义这种形态的函数：

  • register_interest_generator(interest: string) -> Iterator[Message]

你需要写成类似这样的形式：

  • create_interest_task_and_return_success_immediately
  (interest: string, context_queue_callback: Callable[Message]) -> 
    Literal["in_progress", "canceled", "success", "failure"]

关于这一主题的更多讨论，参见下文的执行异步推理任务一节。

随着 LLM 和 API 不断演进以更好地支持多模态对话用例，我们非常希望看到 LLM 研究者探索围绕异步函数以及充当生成器的长时间运行函数的各种想法。

5.11.7 并行与复合函数调用

并行函数调用是指 LLM 可以在单次推理响应中请求多个函数调用。复合函数调用是指 LLM 可以灵活地连续调用多个函数，将函数串联起来以执行复杂操作。

这些能力令人兴奋！

但它们也增加了语音智能体行为的变异性。这意味着你需要开发评测和监控，来检验并行与复合函数调用在真实对话中是否按预期工作。

处理并行函数调用会让你的智能体代码更复杂。我们通常建议，除非有特定用途，否则关闭并行函数调用。

复合函数调用在表现良好时感觉像魔法。我们最喜欢的一个早期例子，是看到 Claude Sonnet 3.5 把多个函数串联起来，根据文件名和时间戳从文件中加载资源。

User: Claude, load the most recent picture I have of the Eiffel Tower.

function call response: <['eiffel_tower_1735838843.jpg', 'empire_state_building_1736374013.jpg', 'eiffel_tower_1737814100.jpg', 'eiffel_tower_1737609270.jpg',
'burj_khalifa_1737348929.jpg']
function call request: <load_resource('eiffel_tower_1737814100.jpg')>
function call response: <{ 'success': 'Image loaded successfully', 'image': … }>

Tower on a cloudy day.

LLM 自己琢磨出如何串联两个函数—— list_files() 和 load_resource()——来响应一条具体指令。这两个函数是在工具列表中描述的，但这种串联行为并没有在提示词中要求。

复合函数调用是最先进 LLM 的一项相对较新的能力。其表现是“参差不齐”的——好得出乎意料，但也让人沮丧地不稳定。

5.12. 多模态

如今的 LLM 除了文本之外，还能消费和生成音频、图像与视频。

我们前面谈到过语音到语音模型。这类模型能够以音频作为输入，并产生音频作为输出。

最先进模型的多模态能力正在快速进步。

GPT、Gemini 和 Claude 模型都有非常好的视觉能力——它们都接受图像作为输入。这些模型的视觉支持最初聚焦于描述图像内容以及转录图像中出现的文字。能力随着每次发布而扩展。数物体、识别边界框、更好地理解图像中物体之间的关系，这些都是较新版本中已经具备的实用能力。

Gemini Flash 可以对视频输入进行推理，包括同时理解视频和音频两条轨道。[40]

有一类有趣的新兴语音应用是：助手能够“看到”你的屏幕，并帮助你在本地机器或网页浏览器上执行任务。已经有不少人构建了语音驱动网页浏览的脚手架。

我们认识的几位程序员，如今说话和打字的量不相上下。把语音输入接到 Claude Code[41] 和 Codex 上是相当容易的。同样也可以接入屏幕捕获，让你的 AI 编程助手看到你所看到的一切——编辑器里的代码、你正在构建的 Web 应用的 UI 状态、终端里的 Python 堆栈跟踪。这种完全多模态的 AI 编程助手，感觉又是我们在本文档中通篇谈到的那种对未来的惊鸿一瞥。[42]

[40] 你也可以用 GPT-4o 和 Claude 处理视频：从视频中抽取单帧，并把这些帧作为图像嵌入到上下文中。这种方法有局限，但对某些“视频”用例效果不错。

[41] 参见 Pipecat MCP Server 包——https://github.com/pipecat-ai/pipecat-mcp-server

[42] 参见 swyx 在 2024 年 OpenAI Dev Day 新加坡站的演讲，《Engineering AI Agents》。

眼下，所有最先进的模型都以不同的组合方式支持多模态。

  • GPT-4.1 支持文本和图像输入，输出文本。
  • gpt-realtime 支持文本、音频和图像输入，输出文本和音频。
  • Gemini Flash 支持文本、音频、图像和视频输入，但只输出文本。
  • OpenAI 的语音转文本和文本转语音模型是完全可控的，构建在 gpt-4o 基础之上，但专门用于文本与音频之间的转换：gpt-4o-transcribe、gpt-4o-mini-transcribe 和 gpt-4o-mini-tts。

多模态支持正在快速演进，我们预计上面这份清单很快就会过时！

对语音 AI 而言，多模态最大的挑战在于音频和图像会消耗大量 token，而更多 token 意味着更高的延迟。

示例媒体 近似 token 数

一分钟语音音频以音频形式 2,000
一张图像 250
一分钟视频 15,000

对某些应用来说，一项重大工程挑战是在处理大量图像的同时实现对话级延迟。对话级延迟要求要么把上下文保持在较小规模，要么依赖服务商特有的缓存 API。而图像会给上下文增加大量 token。

想象一个始终在你的电脑上运行、并把观察你的屏幕作为其工作循环一部分的个人助手智能体。你可能希望能这样问：“大约一小时前我正要读一条推文，结果来了个电话，然后我忘了这事就把标签页关了。那条推文讲的是什么？”

一小时前的内容相当于将近一百万个 token。即使你的模型上下文能容纳一百万个 token[43]，每一轮都带着这么多 token 进行多轮对话，其成本和延迟也令人望而却步。

[43] 你好，Gemini！

你可以把视频摘要成文本，只在上下文中保留摘要。你可以计算嵌入向量并做类 RAG 的检索。LLM 在特征摘要以及用函数调用触发复杂 RAG 查询这两件事上都相当擅长。但这两种方法的工程实现都很复杂。

归根结底，最大的杠杆是上下文缓存。所有最先进的 API 服务商都提供了某种形式的缓存支持。但对于语音 AI 用例而言，今天的缓存特性都还不完美。我们预计缓存 API 会在今年有所改进，因为多模态、多轮对话的用例正受到训练最先进模型的团队越来越多的关注。

6. 使用多个 AI 模型

如今生产环境中的语音 AI 智能体会组合使用多个深度学习模型。[44]

正如我们所讨论的，典型的语音 AI 处理循环会用语音转文本模型转录用户的语音，把转录文本传给 LLM 生成响应，然后执行文本转语音步骤来生成智能体的语音输出。

此外，如今许多生产环境中的语音智能体都以复杂多样的方式使用多个模型。

[44] 即使是 OpenAI 和 Google 的语音到语音 API，也使用专门的 VAD 和降噪模型来实现轮次检测。

6.1. 使用多个微调模型

大多数语音 AI 智能体使用来自 OpenAI 或 Google（有时是 Anthropic 或 Meta）的最先进[45]模型。使用最新、性能最好的模型很重要，因为语音 AI 工作流通常正好处在模型能力参差不齐的前沿[46]的边缘。语音智能体需要能够遵循复杂指令、以自然的方式与人进行开放式对话，并可靠地使用函数和工具。

[45] SOTA——state of the art（最先进）——是一个被广泛使用的 AI 工程术语，大致意思是“来自领先 AI 实验室的最新大模型”。

但对于某些专门用例，针对对话的不同状态分别微调模型可能是有意义的。微调后的模型可以比大模型更小、更快、运行成本更低，同时在特定任务上的表现同样出色（甚至更好）。

想象一个协助从一个非常庞大的工业供应目录中订购零件的智能体。对于这项任务，你可能会训练若干不同的模型，每个专注于一个不同品类：塑料材料、金属材料、紧固件、管道配件、电气、安全设备等。

[46] 沃顿商学院教授 Ethan Mollick 创造了“jagged frontier”（参差不齐的前沿）一词，用来描述最先进模型能力的那个复杂边缘地带——有时好得惊人，有时糟得让人沮丧。

微调模型通常能够“学会”两个重要类别的东西：

  1. 内嵌知识——模型可以学习事实。
  2. 响应模式——模型可以学会以特定方式转换数据，这也包括学习对话模式和流程。

我们假设的这家工业供应公司拥有大量原始数据：

  • 一个非常庞大的知识库，包含数据表、制造商建议、价格，以及目录中每个零件的内部数据。
  • 与人工客服的文本聊天记录、邮件往来，以及转录后的电话对话。

针对特定对话主题使用微调模型。可以采用多种架构方案。在这个例子中，每一轮对话开始时，由一个路由 LLM 对完整上下文进行分类。

把这些原始数据变成用于微调模型的数据集是一项浩大的工作，但是可行的。所需的数据清洗、数据集创建、模型训练和模型评估，都是已被充分理解的问题。

有一点很重要：不要一上来就直接微调——先从提示词工程开始。

提示词几乎总能达到与微调相同的任务效果。微调的优势在于能够使用更小的模型，这可以转化为更快的推理和更低的成本。[47]

使用提示词，你上手的门槛比微调低得多，迭代速度也快得多。[48]

在最初探索如何为不同对话状态使用不同模型时，把你的提示词看作微型“模型”。你是在通过精心构造一个大型、上下文相关的提示词，来教 LLM 该做什么。

  1. 对于内嵌知识，实现一个搜索能力，从你的知识库中拉取信息，并把搜索结果组装成一个有效的提示词。更多内容参见下文的 RAG 与记忆一节。
  2. 对于响应模式，嵌入你期望模型针对不同问题作出回应的示例。有时，仅仅几个示例就够了。有时，你会需要大量示例——100 个或更多。

[47] 如果你想深入研究提示词与微调的对比，可以看看这两篇经典论文：Language Models Are Few-shot Learners，以及 A Comprehensive Survey of Few-shot Learning。

[48] 遵循经典的工程建议：先让它能跑，再让它跑得快，最后让它跑得便宜。在“让它跑得快”这一环节进行到一半之前，都不要考虑从提示词工程转向微调。（或者根本不要转向。）

6.2. 执行异步推理任务

有时你想让 LLM 执行一项运行时间相对较长的任务。记住，在我们的核心对话循环中，我们的目标是响应时间在一秒左右（或更短）。如果一项任务会超过几秒钟，你有两种选择：

  1. 告诉用户正在发生什么，并请他们等待。“请稍等，我为您查一下……”
  2. 异步执行这项较长的任务，让对话在任务于后台进行的同时得以继续。“我这就为您查一下。在我查的同时，您还有其他问题吗？”

如果你在异步执行一项推理任务，你可能会选择为这项特定任务使用另一个 LLM。（因为它与核心对话循环解耦了。）你可能会用一个对语音响应而言慢得不可接受的 LLM，或者一个你为特定任务微调过的 LLM。

异步推理任务的几个例子：

  • 实现内容“护栏”。（参见内容护栏一节。）
  • 创建一张图像。
  • 生成要在沙箱中运行的代码。

去年推理模型取得的惊人进展，扩展了我们能够要求 LLM 做的事情。不过你不能把这些模型用于语音 AI 对话循环，因为它们在输出可用内容之前，往往会花相当长的时间生成思考 token。但是，把推理模型作为多模型语音 AI 架构中的异步部分，效果可以很好。

异步推理通常由 LLM 的函数调用来触发。一种简单的做法是定义两个函数。

  • perform_async_inference()——当 LLM 判断需要运行某个长耗时推理任务时会调用它。你可以定义不止一个这样的函数。请注意，你需要启动异步任务后立即返回一条基本的任务已成功启动响应，这样函数调用请求消息和响应消息在上下文中的顺序才是正确的。[50]
  • queue_async_context_insertion()——当你的异步推理完成时，由你的编排层调用它。这里的棘手之处在于，你如何把结果插入上下文，取决于你想做什么，以及你所使用的 LLM/API 允许什么。一种做法是等待任何进行中的对话轮次结束（包括所有函数调用的完成），把异步推理结果放进一条精心构造的用户消息里，然后再运行一轮对话。

[50] 参见异步函数调用。

6.3. 内容护栏

语音 AI 智能体存在若干脆弱点，会给某些用例带来重大问题。

  • 提示词注入
  • 幻觉
  • 知识过时
  • 生成不恰当或不安全的内容

内容护栏是一个统称，指那些试图检测上述任一问题的代码——既保护 LLM 免受意外和恶意的提示词注入，也在不良 LLM 输出发送给用户之前将其拦截。

为护栏使用一个（或多个）专门的模型有几个潜在优势：

  • 小模型可能很适合做护栏和安全监控。识别问题内容可以是一项相对专门的任务。（事实上，特别是就提示词注入缓解而言，你未必希望使用一个可以被完全通用地提示的模型。）
  • 为护栏工作使用不同的模型，好处在于它不会与你的主模型有一模一样的弱点。至少理论上如此。

有几个开源智能体框架带有护栏组件。

  • llama-guard 是 Meta llama-stack 的一部分
  • NeMO Guardrails 是一个开源工具包，用于为基于 LLM 的对话应用添加可编程护栏

NVIDIA NeMo Guardrails 框架支持的五种护栏类型。图示来自 NeMo Guardrails 文档。

这两个框架在设计时考虑的都是文本聊天，而非语音 AI。但两者都有有用的思路和抽象，如果你正在思考护栏、安全和内容审核，它们值得一看。

值得注意的是，与一年前相比，LLM 在避免所有这些问题上已经好得多了。

对于大型实验室的最新模型来说，幻觉总体上已不再是一个重大问题。如今我们只会经常看到两类幻觉。

  • LLM “假装”调用了某个函数，但实际上并没有调用。这可以通过提示词来修复。你需要好的评测来确保你的提示词中不存在发生这种情况的场景。当你在评测中看到函数调用幻觉时，就迭代你的提示词，直到不再看到为止。（记住，多轮对话会极大地压榨 LLM 的函数调用能力，所以你的评测需要还原你真实的多轮对话场景。）
  • 当你期望 LLM 做网页搜索时它却产生了幻觉。内置的搜索接地（search grounding）是 LLM API 的一项相对较新的特性。LLM 是否会选择执行搜索，目前仍有些难以预测。如果它们不搜索，可能会用其权重中内嵌的（较旧的）知识来回答，或者干脆产生幻觉。与函数调用幻觉不同，这一点并不容易通过提示词修复。但要判断搜索是否真的执行了却很容易。因此你可以把这个信息展示在应用 UI 中，或者注入到语音对话里。如果你的应用依赖网页搜索，这样做是个好主意。你是在把问题推给用户去理解和处理，但这比向用户隐藏“搜了”与“没搜”的区别要好。好的一面是，当搜索接地确实生效时，它在很大程度上可以消除知识过时的问题。

各大实验室的 API 都有非常好的内容安全过滤器。

提示词注入的缓解也比一年前好得多，但随着 LLM 获得新能力，潜在的提示词注入攻击面也在扩大。例如，来自图像中文字的提示词注入现在就成了一个问题。

作为一条非常非常笼统的指引：今天在语音 AI 用例中，你不太可能看到由正常用户行为引发的意外提示词注入。但仅通过用户输入，就完全有可能以颠覆系统指令的方式引导 LLM 的行为。带着这一点来测试你的智能体很重要。特别重要的是，要对 LLM 生成的、流向任何访问后端系统的函数的输入进行清洗和交叉校验。

6.4. 执行单次推理动作

对 AI 工程师来说，学会如何利用 LLM 是一个持续的过程。这个过程的一部分，是我们思考这些新工具方式上的心态转变。当我们刚开始使用 LLM 时，我们大多数人都是通过这样一个视角来看待它们的：语言模型独有的能力是什么？但 LLM 是通用工具。它们擅长范围极广的信息处理任务。

在语音智能体的场景下，我们总是已经准备好了一条执行 LLM 推理的代码路径。我们不必把自己限制为只在核心对话循环中使用 LLM。

例如：

  • 任何时候你想伸手去写正则表达式，你大概都可以改成写一个提示词。
  • 对 LLM 输出做后处理往往很有用。例如，你可能想以两种格式生成输出：用于 UI 展示的文本，以及用于交互式对话的语音。你可以提示对话 LLM 生成格式优美的 markdown 文本，然后再提示 LLM 一次，把文本缩短并重新排版以供语音生成使用。[51]
  • 递归很强大。[52]你可以做这样的事情：让一个 LLM 生成一个列表，然后再调用这个 LLM 对列表的每个元素执行操作。
  • 事实证明，你经常需要为多轮对话做摘要。LLM 是出色的、可控的摘要器。更多内容参见下文的脚本化与指令遵循一节。

[51] 关于对 LLM 输出做后处理，另请参见上文的内容护栏一节。

[52] 我们是程序员，我们当然会 ……——编者注。

这些正在涌现的代码模式中，有许多看起来都像是语言模型把自己、或者把另一个语言模型当作工具来使用。

这是一个如此强大的想法，以至于我们预计 2026 年会有很多人在这上面投入工作。智能体框架可以把对这种模式的支持构建进它们的库级 API 中。模型也可以被训练成递归地执行推理，其方式大致类似于训练它们调用函数和执行代码。

6.5. 迈向自我改进的系统

当我们通过 API 访问一个最先进的“模型”时，我们访问的并不是单一的产物。这些 API 背后的系统使用了各种路由、多阶段处理和分布式系统技术，以快速、灵活、可靠且规模惊人的方式执行推理。这些系统一直在被调整。权重会更新。底层推理实现持续变得更高效。系统架构也在演进。

各大实验室正在不断缩短“用户如何使用其 API”与“它们如何实现推理及其他能力”之间的反馈回路。

这些越来越快的反馈回路，是当下惊人的宏观层面 AI 进步的重要组成部分。

7. 脚本化与指令遵循

一年前，能够打造一个能够进行开放式对话、具有人类自然延迟的语音代理，已经令人兴奋。

如今我们正在部署语音 AI 智能体去完成复杂的真实世界任务。对于今天的用例，我们需要指示 LLM 在一次会话中专注于特定目标。而且我们常常需要 LLM 按特定顺序执行子任务。

例如，在医疗患者接诊工作流中，我们希望智能体：

  • 在做任何其他事情之前，先核实患者身份。
  • 务必询问患者目前正在服用哪些药物。
  • 如果患者说自己在服用药物 X，就问一个特定的追问问题。
  • 诸如此类……

我们把精心构造分步工作流称为脚本化。过去一年语音 AI 开发中的一条经验是：仅靠提示词工程很难实现脚本化的可靠性。

单个提示词能塞进去的细节是有限的。与此相关的是，随着多轮对话中上下文的增长，LLM 需要跟踪的信息越来越多，指令遵循的准确率会下降。

许多语音 AI 开发者正在转向用状态机的方法来构建复杂工作流。我们可以定义一系列状态，而不是写一份冗长详细的系统指令来引导 LLM。每个状态包含：

  • 一份系统指令和一个工具列表。
  • 一段对话上下文。
  • 一个或多个从当前状态通往另一状态的出口。

每次状态转换都是一次机会，可以用来：

  • 更新系统指令和工具列表。
  • 对上下文做摘要或修改。[53]

[53] 通常，你会调用一次 LLM 推理来执行上下文摘要。:-)

状态机方法之所以奏效，是因为更短、更聚焦的系统指令、工具列表和上下文，能显著提升 LLM 的指令遵循能力。

挑战在于找到恰当的平衡：一方面利用 LLM 进行开放式自然对话的能力，另一方面确保 LLM 可靠地完成待办工作中那些重要的部分。

Pipecat Flows 是构建在 Pipecat 之上的一个库，帮助开发者创建工作流状态机。

状态图以 JSON 表示，可以加载进 Pipecat 进程。还有一个图形化编辑器用于创建这些 JSON 状态图。

AI 研发中一个活跃的领域是多智能体系统。你可以把一个工作流看作多智能体系统，而不是一系列需要遍历的状态。

Pipecat 的核心架构组件之一是并行流水线。并行流水线允许你把流经处理图的数据拆分出来，对其操作两次（或更多次）。你可以阻塞和过滤数据。你可以定义多条并行流水线。你可以把一个工作流看作一组带门控、相互协调的并行流水线。

8. 语音 AI 评测

有一类非常重要的工具就是评测（eval，evaluation 的简称）。

评测是一个机器学习术语，指用来评估系统能力并判断其质量的工具或流程。

8.1. 语音 AI 评测不同于软件单元测试

如果你有传统软件工程的经验，你可能已经习惯把测试看作（几乎）确定性的任务。

语音人工智能需要的测试与传统软件工程不同。 语音AI的输出是非确定性的。 语音AI测试的输入是一个复杂、分支且多回合的对话。

你不再是测试“某个特定输入产生某个特定输出 (f(x) = y)”，而是需要进行概率评估。 换句话说，你需要运行多次测试，看看某些事件发生的频率。[54]对某些测试来说，一类场景十次做对八次就可接受；对另一些测试，准确率需要达到 9.99/10。

[54] 用户请求是否得到了满足、智能体是否打断了用户、智能体是否跑题了，等等

你不再只有一个输入，而是会有很多个：所有用户的回应。因此，在不模拟用户行为的情况下，很难测试语音AI应用。

最后，语音 AI 测试的结果不是二元的，很少会像传统单元测试那样给出确定的 ✅ 或 ❌。相反，你需要审阅结果并权衡取舍。

8.2. Failure modes（失败模式）

测试、评估和监控语音AI应用具有挑战性。 语音代理是多模型和多模态的。 延迟非常重要。

如今，经常面临挑战的领域包括以下：

  • 首字发声时间（time-to-first-speech）和智能体响应时间（time-to-agent-response）的延迟。
  • 转录错误。
  • 理解和口述地址、邮箱、姓名、电话号码。
  • 打断。

8.3. 制定评测策略

一个初步的评测流程可简单到只包含一张提示词和测试用例的表格。

一种典型做法是：每当你测试一个新模型或改动系统的主要部分时，就运行每一条提示词，并用一个 LLM 来判断响应是否落在某个预期参数定义的范围之内。

Pipecat包含核心功能，帮助你建立自己的评分。 其预期用途是“闭环”，即编码代理可以在开发过程中迭代测试代理。

有一个基础评测，比完全没有评测要好得多。但随着你开始规模化运营，投入资源做评测——拥有真正优秀的评测——就变得至关重要。

为语音 AI 用例提供精细工具的评测平台才刚刚开始出现。在开发音频评测、测试、模拟与监控工具方面走在前列的几个平台是 Cekura、Coval 和 Bluejay。这三家都有出色的 Pipecat 集成。

Coval 评测平台 UI 的一张截图

这些平台可以在以下方面提供帮助：

  • 提示词迭代。
  • 面向音频、工作流、函数调用以及对话语义评估的现成指标。
  • 在问题领域上持续爬坡改进（例如，让你的智能体更擅长处理打断）。
  • 回归测试（确保你在修复一个问题领域时，不会在其他此前已解决的问题领域引入回退）。
  • 跟踪性能随时间的变化——既包括开发者所做的变更带来的变化，也包括跨用户群体的变化。

9. 与电话基础设施集成

今天增长最快的语音 AI 用例，大多数都涉及电话通话。AI 语音智能体如今正在大规模地接听和拨打电话。

其中一部分发生在传统呼叫中心。呼叫中心大多把语音 AI 看作一种能够提升“转接率”的技术——也就是可以由自动化而非人工坐席处理的通话占比。这使得采用语音 AI 的投资回报非常清晰。如果 LLM 的每分钟成本低于人工坐席，采购决策就很容易做了。[55]

[55] 当然，前提是 AI 智能体的表现足够好。而对于今天种类繁多的客户支持用例来说，它确实够好。

不过，除了简单的投资回报计算之外，还有几件有意思的事情正在加速这一采用过程。

语音 AI 智能体的可扩展性是人工团队所不具备的。一旦语音 AI 部署到位，高峰时段的等待时间就会下降。（客户满意度评分随之直接上升。）

而且 LLM 有时能比人工坐席做得更好，因为我们给了它们更好的工具。在许多客户支持场景中，人工坐席必须同时应付多个遗留后端系统。及时找到信息可能就是个难题。而当我们把语音 AI 部署到同样的场景中时，我们必须为这些遗留系统构建 API 级别的访问能力。全新的“LLM 加 API”层正在推动向语音 AI 的技术转型。

很明显，生成式 AI 将在未来几年彻底重塑呼叫中心的格局。

在呼叫中心之外，语音 AI 正在改变小型企业接听电话的方式，以及它们如何利用电话进行信息发现和协调。我们每天都在与初创公司交流，它们在你听说过的每一个商业垂直领域构建专门的 AI 电话解决方案。

这个领域的人经常开玩笑说，很快人类就完全不会拨打或接听电话了。所有电话都会是 AI 对 AI。从我们看到的趋势线来判断，这话有几分道理！

如果你对语音 AI 的电话技术感兴趣，有几个缩写和常见概念你应该熟悉。

  • PSTN 是公共交换电话网络。如果你需要与一部有电话号码的真实电话交互，你就需要与 PSTN 平台打交道。Twilio 就是几乎每个开发者都听说过的 PSTN 平台。
  • SIP 是用于 IP 电话的一种特定协议，但在一般意义上，SIP 被用来指代系统之间的电话互联。例如，如果你要对接呼叫中心的技术栈，你就需要使用 SIP。你可以与 SIP 服务商合作，也可以自建 SIP 服务器。
  • DTMF 音是用来在电话菜单中导航的按键音。语音智能体需要能够发送 DTMF 音，才能与真实世界的电话系统交互。LLM 在处理电话树方面相当不错。你只需要做一点提示词工程，并定义发送 DTMF 音的函数。
  • 语音智能体常常需要执行呼叫转接。在简单转接中，语音 AI 通过调用一个触发呼叫转接的函数退出会话。[56]温转接（warm transfer）是从一个坐席交接到另一个坐席，两个坐席在把来电者转给第二个坐席之前会先互相交谈。语音 AI 智能体也能做温转接，就像人类一样。语音智能体先与人类来电者交谈，然后让来电者进入等待，与被拉进这通电话的新的人工坐席进行一段对话，最后把人类来电者接到人工坐席上。

[56] 实际的转接操作可能是对你的电话平台的一次 API 调用，或者是一个 SIP REFER 动作。

10. RAG 与记忆

语音 AI 智能体经常需要从外部系统访问信息。例如，你可能需要：

  • 将用户信息整合进LLM的系统指令中
  • 检索以往对话历史。
  • 在知识库中查找信息。
  • 执行一次网页搜索。
  • 做实时库存或订单状态查询。

这些全都属于 RAG(检索增强生成)的范畴。RAG 是把信息检索与 LLM 提示相结合的通用 AI 工程术语。

对语音智能体而言，“最简单的 RAG”是在对话开始之前查询关于用户的信息，然后把这些信息合并进 LLM 的系统指令。

user_info = fetch_user_info(user_id)

system_prompt_base = "You are a voice AI assistant..."

system_prompt = (
  system_prompt_base
  + f"""
The name of the patient is {user_info["name"]}.
The patient is {user_info["age"]} years old.
The patient has the following medical history: {user_info["summarized_history"]}.
"""
)

简单 RAG——在会话开始时执行一次查询

RAG 是一个很深的话题，也是一个快速变化的领域。[57]技术手段的范围从上面那种只使用基本查询和字符串插值的相对简单的做法，一直到使用嵌入向量和向量数据库来组织海量半结构化数据的系统。

[57] 嗯。这听起来跟如今生成式 AI 的每一个其他领域都一样。

通常，80/20 法则的做法就能让你走得很远。如果你已有知识库，就用你已有的 API。写一些简单的评测，这样你就可以测试几种不同的格式，把查询结果注入到对话上下文中。部署到生产环境，然后监控它在真实用户身上的表现如何。

async def query_order_system(function_name, tool_call_id, args, llm, context, result_callback):
  "First push a speech frame. This is handy when the LLM response might take a while."
  await llm.push_frame(TTSSpeakFrame("Please hold on while I look that order up for you."))

  query_result = order_system.get(args["query"])
  await result_callback({
    "info": json.dumps({
     "lookup_success": True,
     "order_status": query_result["order_status"],
     "delivery_date": query_result["delivery_date"],
    })
 })

llm.register_function("query_order_system", query_order_system)

会话过程中的 RAG。为 LLM 定义一个在需要查询信息时调用的函数。在这个例子中，我们还会播出一句预设的口头语，让用户知道系统需要几秒钟才能响应。

一如既往，与非语音 AI 系统相比，延迟在语音 AI 中是更大的挑战。当 LLM 发出函数调用请求时，额外的推理调用会增加延迟。在外部系统中查询信息也可能很慢。在执行 RAG 查询之前先触发一段简单的语音输出，让用户知道工作正在进行中，这往往很有用。

更广泛地说，跨会话的记忆是一项有用的能力。想象一个需要记住你谈过的所有事情的语音 AI 个人助理。两种通用方法是：

  1. 把每段对话保存到持久化存储中。测试几种把对话加载进上下文的方式。例如，对个人助理用例来说一种效果很好的策略是：智能体启动时始终完整加载最近的一段对话，加载最近 N 段对话的摘要，并定义一个查询函数，让 LLM 在需要时能够动态加载更早的对话。
  2. 把对话历史中的每条消息连同消息图的元数据一起，分别保存到数据库中。为每条消息建立索引（也许使用语义嵌入向量）。这让你能够动态构建带分支的对话历史。如果你的应用大量使用图像输入（LLM 视觉），你可能会想这么做。图像会占用大量上下文空间！[58]这种方法还让你能够构建带分支的 UI，而这正是 AI 应用设计师们才刚刚开始探索的方向。

[58] 参见多模态。

11. 托管与扩展

语音 AI 应用通常有一些传统的应用组件——Web 应用前端、API 端点以及其他后端元素。但智能体进程本身与传统应用组件差异足够大，以至于部署和扩展语音 AI 会带来独有的挑战。

11.1. 架构

  • 语音 AI 智能体的对话循环通常是一个长时间运行的进程（而不是一个在单次响应生成完毕后就退出的请求/响应函数）。
  • 语音智能体实时流式传输音频。任何让流式传输停滞的因素都可能造成音频毛刺。（共享虚拟机上的 CPU 尖峰、哪怕只阻塞音频线程执行 10 毫秒的程序流程，等等。）
  • 语音智能体通常需要 WebSocket 或 WebRTC 连接。云服务的网络网关和路由产品对 WebSockets 的支持远不如对 HTTP 的支持好。它们往往完全不支持 UDP。（而 WebRTC 需要 UDP。）

由于所有这些原因，通常无法把 AWS Lambda 或 Google Cloud Run 这类无服务器框架用于语音 AI。

今天部署语音 AI 智能体的最佳实践是：

  • 一旦你度过了原型阶段，就投入工程时间创建轻量级工具，用来构建 Docker（或类似的）容器以部署你的智能体。
  • 把你的容器推送到你选择的计算平台上。对于简单的部署，你可以就保持固定数量的虚拟机一直运行。但到了某个阶段，你会希望接入平台的工具链，以便实现自动扩缩容、优雅地部署新版本、实现良好的服务发现与故障转移，并构建其他规模化运维所需的能力。
  • 如今 Kubernetes 是管理容器、部署和扩缩容的标准。Kubernetes 学习曲线很陡，但在所有主要云平台上都得到支持。Kubernetes 周边有着非常庞大的生态系统。
  • 在部署软件更新时，你会希望设置较长的排空时间（drain time），让现有连接保持存活直到会话结束。这在 Kubernetes 中做起来不算太难，但细节取决于你的 k8s 引擎和版本。
  • 冷启动对语音 AI 智能体来说是个问题，因为快速建立连接很重要。维持一个空闲的智能体池是避免长冷启动最简单的办法。如果你的工作负载不需要在本地运行大模型，通常你不必花太大力气就能实现快速的容器冷启动。[59]

虚拟机规格和容器装箱（packing）常常在人们第一次部署到生产环境时绊住他们。你的智能体所需的规格会因你使用的库以及你在智能体进程内做了多少 CPU 密集型工作而不同。一条好的经验法则是：从每台虚拟机 CPU 运行一个智能体开始，内存则给到你在开发机上观察到的单个智能体进程最大消耗量的两倍。[60]

Daily 的 Pipecat Cloud 智能体托管平台替你管理了所有的 Kubernetes 痛点。你可以用 "docker push" 把你的 Pipecat 智能体推送到 Pipecat Cloud，并在多个全球区域规模化运行它们，同时获得原生的电话与 WebRTC 网络支持。

[59] 如果你在本地运行大模型，关于冷启动的建议远远超出了本指南的范围。如果你还不是 GPU 和容器优化方面的专家，你大概应该去找一位专家，而不是自己去爬那条学习曲线（至少等到你的运营规模足够大、能够摊薄开发所需工具的成本时再说）。

[60] 确保你的容器运行时把新的智能体进程调度到空闲的 CPU 上。这并不总是 k8s 的默认行为。

11.2. 计算每分钟成本

语音AI的成本因模型、API和托管基础设施而有很大差异。 费用也取决于具体使用场景。例如，正如成本比较中所讨论的，会话越长，每分钟成本通常越高。而电话比 WebRTC 传输更贵。

成本区间是：如果你使用像 OpenAI Realtime API 这样的语音到语音 API，每分钟 $0.20 或更高；一站式托管智能体平台每分钟 $0.10；而高度成本优化、运行在相当规模上的部署可以低至每分钟 $0.02。

我们有时会看到人们犯的一个错误是：在还没计算语音和 LLM API 成本之前，就先对智能体托管本身做成本优化。一般来说，智能体进程本身的云运行时成本占每分钟总成本的比重不到百分之一。花工程精力优化每个vCPU的并发代理数量并不划算。

12. 2026 与 2027 年会发生什么

语音智能体如今已在呼叫中心和其他企业用例中大规模部署。谈到语音AI的更广泛潜力，我们才刚触及皮毛。

在 2026 年，我们最为兴奋的一些话题包括：

在单个“智能体”中使用子智能体、多个模型和多个推理循环的新编程抽象。生产环境中的语音智能体正越来越多地使用一个模型来跑语音对话流水线，同时也启动、停止并引导子智能体，用于专门处理和长耗时的智能体化子流程。

带语音接口的机器人与实体 AI 设备是一大片开发领域。例如可以看看 NVIDIA ACE Controller 库。

今天的 AI 原生应用本质上是多模态的：输入和输出都同时有语音和文本；来自摄像头的图像输入，从而让智能体能看到你屏幕上显示的内容；以及部分由 LLM 实时生成的动态用户界面。

而最宏观的趋势或许是：一切都在朝着自然语言与持续学习的方向演进。大语言模型是如此强大的语言处理引擎：我们正在学习如何用自然语言来描述一切，如何让这些“自然语言系统”可组合，以及如何构建能够自动改进智能体的循环。
